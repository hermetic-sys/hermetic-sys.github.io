Why every credential manager on Linux has the same vulnerability.

And how two forgotten kernel primitives close it.

The Hermetic Project · April 17, 2026 · updated November 2026
researchlinuxsecurityai-agents
Moved and updated November 2026. This essay first appeared on the Hermetic homepage in April 2026. Section 6 named running the broker under a separate user as the next milestone; what shipped instead is the agent shield, noted in place. Mechanism names are kept because they are the essay's subject.

1. The assumption everyone makes

Every credential manager on Linux trusts the same boundary: the Unix user ID. If a process runs as your UID, it can connect to your SSH agent socket, read your HashiCorp Vault token, access credentials in your environment variables, and communicate with any daemon you own. This is not a bug in any individual product. It is the shared, unexamined foundation of Linux credential security.

Major password managers and credential tools document that their SSH agents restrict access solely by file permissions on the agent socket or named pipe. Secret management systems authenticate clients using bearer tokens that carry no process-level identity. CLI credential helpers inject temporary credentials as environment variables readable by any same-UID process via /proc/pid/environ. Products following this pattern include 1Password, HashiCorp Vault, aws-vault, OpenSSH's ssh-agent, and GPG's gpg-agent.

The reasoning was straightforward and, until recently, correct. If an attacker is already executing code as your user, they can read every file you own — browser cookies, shell history, cloud credentials, SSH keys. Protecting one daemon's socket while every flat file on disk is readable would be security theater. The accepted wisdom: if they are running code as you, you have already lost.

This paper argues that this assumption is now wrong, explains why, demonstrates a specific exploit that breaks the most common fix, and describes the correct solution.

2. What changed: AI agents execute code by design

AI coding agents changed the equation. Claude Code, GitHub Copilot, Cursor, Windsurf, and similar tools routinely execute shell commands as the user's UID. This is their intended functionality, not an exploit. The agent reads a task description, generates a shell command, and executes it.

These agents are susceptible to prompt injection. Attacker-controlled text in a GitHub issue, a code comment, a pull request description, or an API error response can redirect the agent's behavior. A carefully crafted comment can instruct the agent to read credentials from a daemon socket and exfiltrate them.

The supply chain attack vector already demonstrated this pattern. The event-stream npm compromise (2018), the ua-parser-js attack (2021), and the Axios npm supply-chain attack (March 2026, affecting millions of weekly downloads) all executed automated credential theft under the developer's UID. AI agents collapse the attack further: a poisoned comment in a repository the agent is working on is sufficient.

⚠ Every precondition for same-UID credential theft is the default state for developers using AI coding agents. This is not a theoretical risk. It is the expected operating environment.

3. The obvious fix: binary attestation via /proc/pid/exe

The obvious fix is process identity verification. On Linux, the kernel exposes the executable path of any process via /proc/pid/exe, a special symbolic link that resolves to the binary loaded during execve(). Unlike /proc/pid/cmdline, which the process can modify at any time, /proc/pid/exe is set by the kernel and cannot be changed without CAP_SYS_ADMIN.

A robust implementation opens /proc/peer_pid/exe as a file descriptor, reads the binary contents, and computes a SHA-256 hash. It compares this against its own hash, computed from /proc/self/exe at startup. A hash mismatch means the connecting process is not the expected binary.

This approach has real precedent. SPIFFE/SPIRE's Unix Workload Attestor uses /proc/pid/exe to identify workloads. Polkit historically used it for authorization decisions. Snapd uses it for snap confinement verification. It works. Until it doesn't.

4. Two exploits that break binary attestation

4.1 The FD-sharing race

Binary attestation via /proc/pid/exe has a time-of-check-to-time-of-use vulnerability. File descriptors survive fork() and exec(). This creates an attack chain:

Step 1. The attacker's Python script creates a Unix socket connected to the daemon. Step 2. The script calls fork(). The child inherits the socket fd. Step 3. The child calls execve() on the legitimate binary — its /proc/pid/exe now points to the real binary. Step 4. The parent (still Python) sends an attestation request on the shared socket. SO_PEERCRED returns the child's PID; the daemon reads the child's /proc/pid/exe; hash matches; token issued. Step 5. The parent receives the token and has authenticated access.

During adversarial validation, an AI attack simulation produced a working exploit script that extracted a valid session token. We attempted multiple mitigations including accept-time hashing, challenge-response protocols, and per-PID token binding. All failed because the attacker controls the timing of execve() — the child becomes the legitimate binary before any daemon code runs.

◆ The FD-sharing exploit was discovered and operationalized by an AI adversarial auditor during our security validation — demonstrating that the same AI capabilities that enable prompt-injection attacks can also find and exploit credential infrastructure vulnerabilities.

This vulnerability class is not new. CVE-2013-4288 in polkit exploited the same TOCTOU pattern, triggering a cascade of seven related CVEs. CVE-2019-5736 in runc exploited /proc/pid/exe in the opposite direction. Yet every credential manager that uses socket-level authentication still relies on SO_PEERCRED alone.

4.2 Token theft via /proc/pid/mem

There is a subtler attack that survives even after the FD-sharing race is closed. Binary attestation requires the daemon to read /proc/peer_pid/exe. This requires the client's dumpable attribute to be 1. Setting PR_SET_DUMPABLE=0 blocks the read. The client must keep DUMPABLE=1 during attestation, then set it to 0 after receiving the session token.

That constraint opens a window. Between process start and attestation completion, the client's /proc/pid/mem is readable by any same-UID process. On Linux, file descriptor permissions are evaluated at open() time. Once granted, subsequent dumpable changes do not revoke the fd. If the session token is a bearer credential — valid from any process, any PID — an attacker who extracts it from memory can present it from their own process and gain full authenticated access.

⚠ The attestation window that enables binary verification also creates a memory-read window. The defense creates the vulnerability. This tension is inherent to any /proc-based attestation scheme on Linux.

5. Two fixes, both already in the kernel

5.1 Sender verification: SCM_CREDENTIALS

The FD-sharing race exploits a semantic mismatch. SO_PEERCRED answers "who called connect()?" The credentials are recorded once and never updated. After fork(), the parent inherits the fd but SO_PEERCRED still identifies the child.

The Linux kernel has provided the correct mechanism since version 2.2: SCM_CREDENTIALS. When a socket has SO_PASSCRED enabled, the kernel attaches the sender's credentials (PID, UID, GID) to every message via recvmsg(). These are verified by the kernel at send time. Unforgeable without CAP_SYS_ADMIN.

With this primitive, the daemon can verify on every single incoming message that the sender is the same process that originally connected — not a forked child that inherited the socket. The FD-sharing race closes because the kernel itself refuses to lie about who called sendmsg().

5.2 Token binding: tokens are not bearer credentials

SCM_CREDENTIALS closes the FD-sharing race but does not close the /proc/pid/mem attack. That attack uses a clean connection with no fd sharing.

The fix is to bind the token to the process that attested. When the daemon issues a session token, it records the attesting process's PID. On every subsequent request, it compares the presenting PID against the stored PID. A mismatch means someone other than the original attestor is using the token.

The stolen token becomes worthless. The attacker reads it from memory in one process, presents it from another, and the daemon rejects it because the PIDs differ. Combined with SCM_CREDENTIALS, these close both the FD-sharing race and the memory-theft vector using only kernel primitives.

The stolen token is now worthless. The attacker reads it from memory (PID Y), presents it from Python (PID X), and the daemon rejects it because X ≠ Y.

✓ Both fixes use kernel primitives that have existed for decades. SCM_CREDENTIALS: Linux 2.2, January 1999. SO_PEERCRED PID for token binding: available since Unix domain sockets were introduced. The mechanisms that close these vulnerabilities were always there.

6. Defense in depth

Sender verification and PID-bound tokens close two specific vulnerabilities, but a credential daemon on Linux needs more. PR_SET_DUMPABLE=0 blocks same-UID processes from reading /proc/pid/exe, /proc/pid/mem, /proc/pid/environ, and /proc/pid/fd/. The attestation protocol has to complete before DUMPABLE=0 can be set, which creates a narrow window during which tokens must not yet exist in client memory.

Beyond the kernel primitives, a hardened daemon needs library-injection defenses to catch LD_PRELOAD attacks, scoped session tokens with narrow TTLs to limit blast radius, and token delivery channels that don't appear in /proc/pid/environ or /proc/pid/cmdline. Each layer handles a class the others cannot.

No single mechanism is sufficient. Sender verification catches socket-level impersonation. PID binding catches token-level theft. DUMPABLE restrictions catch inspection across the attestation boundary. Scoped tokens limit lateral movement if any component is compromised. These compose into a defense that survives the failure of any single layer.

These layers raise the cost of same-UID extraction from trivial to substantial — they close the FD-sharing race, token replay, and opportunistic memory scraping. They do not make a same-UID attacker with arbitrary code execution impossible; they shrink the window and the blast radius. The architectural close — running the broker under a separate UID the agent cannot reach — is the next milestone.

Update, November 2026. The closure that shipped is different: rather than moving the broker to another user, hermetic shield confines the agent. It runs the agent in its own namespaces where the vault directory and Hermetic's processes cannot be seen, while brokered calls keep working through a relay. It confines the agent and what it launches, not every program you run yourself.

7. What this means for the industry

Every credential manager, secret agent, and authentication daemon on Linux that uses Unix domain sockets for local IPC faces these vulnerabilities. The FD-sharing race exploits the gap between who connected and who is sending. The memory-theft attack exploits the attestation window that binary verification requires. Both are closed by kernel primitives that have existed for decades.

The fixes are not complex. Sender verification uses SCM_CREDENTIALS, a kernel primitive available since Linux 2.2. Token binding uses the PID returned by SO_PEERCRED, available since Unix domain sockets were introduced. Any daemon exposing a Unix socket can adopt both.

We discovered these vulnerabilities while building Hermetic, a credential isolation daemon for AI agents. The cryptographic core and the transport layer are open source (AGPL-3.0-or-later); their public source returns with the public release. The adversarial validation that found both exploits, and the kernel-level fixes, are documented alongside the code.
