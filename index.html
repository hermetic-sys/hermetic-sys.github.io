your API keys.

Not with Hermetic. Your keys live in an encrypted vault on your machine. The agent asks for a call by key name and URL; Hermetic decrypts the key inside its own processes, makes the authenticated HTTPS request and returns only the response. The key never enters the agent's process — not its memory, its context window or its logs.

The pattern

Prompt injection → credential theft is no longer theoretical.

AI coding agents run shell commands as your user. That is the point of them. The same user that owns your .env files owns the agent's shell — and the agent follows instructions it reads, including ones written by a stranger in a README, an issue comment or an API error.

Most credential tools on Linux trust the Unix user boundary: anything running as you gets what you get. That reasoning held when “running code as you” meant you had already lost. An agent changes what it means. The fix is to move the credential somewhere the agent cannot reach, even while it is trying to help.

A typical attack
  1. 1You ask the agent to review a dependency update.
  2. 2The dependency's README hides an instruction block written for the model.
  3. 3The agent follows it: cat ~/.aws/credentials
  4. 4It base64-encodes the file into a commit message.
  5. 5The keys leave your machine in a normal-looking git push.
No bug is exploited. The attack uses the trust model exactly as designed.
How it works

Three ways a key can be used. You decide how far each one travels.

The default is the first one, where the agent only ever sees the response. The other two exist for tools that cannot work any other way — and each is something you switch on, per key.

hermetic_authenticated_request

Agent sees: the response only

The agent calls an MCP tool with a key name and a URL. Hermetic's daemon checks the key's rules and decrypts it; Hermetic's bridge — a separate process, hardened for the length of the request — adds the key to the HTTPS request, makes the call, wipes the key and hands back the status, headers and body. From a terminal, hermetic request does the same.

what the agent sends · what you can type
# MCP tool call from the agent
hermetic_authenticated_request
  secret_name: "stripe"
  url:         "https://api.stripe.com/v1/balance"

# the same call from a terminal
$ hermetic request --secret stripe --url https://api.stripe.com/v1/balance

# the agent gets the API's response — never the key

Requests go over HTTPS only, to the domains the key is bound to. Private and reserved network ranges are refused, and the headers that could redirect or re-authenticate a request are stripped.

hermetic run · hermetic_env_spawn

Off by default: allowed per key

Some tools only read a key from their environment — gh, a cloud CLI, a third-party MCP server. For those, Hermetic starts the program with the key in its environment. Through the MCP tool the agent gets the exit code only; hermetic run redacts the key from the program's output. Shells and script interpreters are refused.

The program does hold the key while it runs, so this path is closed for every new key until you open it for that key.

terminal
# let this one key be handed to programs
$ hermetic tier set github-token env-allowed

# run gh with the token in its environment
$ hermetic run --secret github-token --env-var GH_TOKEN -- gh pr create --fill

hermetic reveal

Off by default: one key at most

A few integrations must read a raw value — an exec credential provider such as OpenClaw's. hermetic reveal prints one key to standard output. Only one key can be the reveal key, choosing it takes your passphrase, and every reveal is rate-limited and written to the audit log. There is no reveal tool for agents.

Be clear about what it means: once a reveal key is set, any program running as your user can read that one key. That is why there is none until you choose one.

terminal
# choose the reveal key (asks for your passphrase)
$ hermetic reveal --set openclaw-llm
# or let the wizard set up OpenClaw end to end
$ hermetic reveal --configure openclaw

New · Agent shield

Put the agent in a box where Hermetic does not exist.

hermetic shield -- claude runs your agent in its own Linux namespaces. Inside, the vault directory and /tmp are empty, the rest of the system is read-only apart from your project and the agent's own config and cache folders, and the Hermetic daemon cannot even be seen. Brokered calls keep working: a relay inside forwards them to a bridge running outside the box.

  • The agent cannot read the vault files, signal or inspect Hermetic's processes, or reach another shield's socket.
  • One bridge service per shield, so every agent is a separate, audited caller.
  • Opt-in and per launch. hermetic doctor warns when no agent is shielded.
  • Needs bubblewrap. Network access is unchanged — that is not Hermetic's job.
What it does not do: it confines the agent, not your whole account. A program you run yourself outside the shield, as your user, can still read the idle bridge service's memory. Handing keys to programs (★★) is refused inside the shield.

$ hermetic shield -- claude
$ hermetic shield --bind ~/projects -- codex

Controls

Decide what each key may do — before the agent tries.

Hiding the key is half the job. A key the agent can use is still a key the agent can misuse, so every key carries its own rules, enforced by the daemon on every brokered call.

Brokered-only by default

New keys never leave Hermetic unless you say so.

Every key you add — in the terminal, the terminal dashboard or by import — is stored brokered-only: the agent can use it through a brokered call, and every attempt to hand it to a program is refused and logged. Open the ★★ path for one key when a tool needs it, and review existing keys in one pass.

terminal
# this one key may be handed to programs
$ hermetic add github-token --env-allowed

# walk every existing key; nothing changes until you confirm
$ hermetic tier review
$ hermetic tier set stripe brokered-only
Per-key rules

Domains, methods, paths — or a ready-made profile.

A key is bound to the domains it may call, and can be narrowed further to specific methods and paths, a request body size, or explicit deny rules. Nine profiles cover common jobs, and a strict/advisory switch lets you watch what a new rule would refuse before you enforce it.

Rules live inside the encrypted vault. Changing them takes your passphrase, so an agent cannot quietly loosen its own limits.

Reference profiles

github-read-only github-commit-bounded github-pr-bounded github-merge-protected slack-post-only notion-read-write-page npm-install-locked db-request-capped db-write-bounded

terminal
$ hermetic bind --secret github-token \
    --profile github-pr-bounded

# log would-be denials first, then enforce
$ hermetic mode advisory
$ hermetic mode strict
Destructive-endpoint floor

Refunds, deletes and mass sends are blocked until you allow them.

Hermetic ships a catalogue of 74 irreversible endpoints across 48 services. On a brokered call, those are refused by default — for every key, in every mode, even where a broad rule would otherwise allow them. Enable one endpoint for one key, or set it to ask first: the call is refused and listed as pending until you approve it from your terminal — once, or for a short window — and the agent retries.

The floor sees method and path, so it applies to brokered calls; keys you let programs hold are outside it — one more reason they are off by default.

Audit

A log you can't quietly rewrite

Every brokered call, refusal, approval and reveal is chained with a keyed hash. A separate tip file catches deleted or rolled-back entries, and hermetic audit --verify fails loudly on tampering. Agents have no tool to read it.

Vault changes

Your passphrase for every write

Adding, rotating or rebinding a key needs a fresh passphrase proof that the daemon checks — from the CLI, the terminal dashboard and the web dashboard alike. Driving an unlocked client is not enough to change the vault.

Diagnostics

hermetic doctor

Checks the daemon, the vault, the audit chain, which keys may leave Hermetic, whether any agent is shielded, and whether a remembered session file is sitting on disk — and suggests a fix for each finding.

MCP proxy

Take the plaintext out of your MCP config files.

Many MCP servers read a token from an environment variable, so the usual setup pastes it into a JSON file any program can read. hermetic proxy starts the server for you with the key injected from the vault, then sits between your agent and the server and watches the traffic.

Before · plaintext in configexposed
claude_desktop_config.json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_R3aL…" }
    }
  }
}
After · resolved from the vault at launchno key on disk
claude_desktop_config.json
{
  "mcpServers": {
    "github": {
      "command": "hermetic",
      "args": ["proxy", "--server", "github",
        "-c", "github-token:GITHUB_PERSONAL_ACCESS_TOKEN",
        "--", "npx", "-y", "@modelcontextprotocol/server-github"]
    }
  }
}
01

Injected at launch

The key comes from the vault when the server starts. Nothing in the config file, nothing in your shell history.

02

Leak scanning

Server responses are scanned before they reach the agent; a credential the server tries to send back is suppressed.

03

Tool pinning

Each tool's description and schema are pinned. A tool that quietly changes, or a new one that appears, is blocked by default.

04

Per-tool rules

Allow or deny tools by name — keep the read tools, drop the ones that delete.

05

Dies with the proxy

The server is tied to the proxy's lifetime and cannot write the key to a crash dump.

06

Logs you can follow

hermetic proxy --logs --follow shows injections, tool calls, policy denials and scanner hits.

What the proxy does not do: the MCP server holds the key while it runs (★★), and any program running as your user can read a running process's environment. So the proxy only works with keys you allow to be handed to programs — use the brokered path wherever a server lets you.
Works with your agent

One command connects it.

hermetic connect finds Claude Code, Cursor, Windsurf or Claude Desktop and writes their MCP configuration. VS Code and others get a config from hermetic mcp-config; any MCP client that speaks stdio works. OpenClaw gets both the MCP tools and an exec credential provider.

Agents get five tools: make an authenticated request, list key names (never values), run a program with an allowed key, lock Hermetic down, and print the command for you to add a key. Pro adds JWT signing. There is no tool that stores or reveals a secret.

Architecture

Open kernel. Hardened binary.

One Rust binary, a local daemon and a Unix socket. No network listener, no cloud account, no telemetry.

Untrusted
AI agent
Talks MCP over stdio. Holds key names, never key values.
Hardened
MCP bridge
Started by the agent. Holds one key for one request, locked down for that window.
CLI · terminal dashboard · web dashboard
Operator surfaces. Every vault change needs a fresh passphrase proof.
Trusted
Daemon
Master key in locked memory · vault · rules · destructive floor · audit chain. Checks every connecting program against its own binary, and every message against the process that connected.
Open source
hermetic-core
Vault, key derivation, encryption, bindings, audit chain.
hermetic-transport
HTTPS client, network-range protection, DNS pinning, header rules.
Cryptography

Argon2id key derivation (memory-hard), AES-256-GCM for every key under its own derived key, an encrypted database underneath, HMAC-SHA256 for the audit chain, rustls for TLS. Standard algorithms, openly chosen.

Process hardening

Memory is locked so keys never swap to disk, other processes cannot attach a debugger, privileges cannot be raised, and core dumps are off. The first three are mandatory: if one fails, the daemon refuses to start.

hermetic-core and hermetic-transport are AGPL-3.0-or-later. The daemon, CLI, MCP bridge, proxy and dashboards are proprietary, shipped as a free Community binary and a paid Pro binary with the same security model. Public source returns with the public release.

Known limitations

Read these before you trust us.

Security through obscurity is not security. Here is what Hermetic does not do.

Partial

Programs running as your own user

A program already running as your Unix user can connect to Hermetic and make brokered calls while it runs — the kernel cannot tell it apart from your agent. It cannot get a key through any agent-facing tool, and it cannot change the vault without your passphrase. It can read a key you allowed to be handed to programs (from that program's environment), the reveal key if you set one, or a copy paged out to unencrypted swap. Hermetic defends the agent and what it launches, and the shield confines the agent itself; software you run yourself outside the shield is outside that boundary.

High · opt-in

The remembered-session file

hermetic start --remember-session stores your passphrase on disk, wrapped with a key that any program running as you can rebuild until the next reboot. It is off unless you ask for it, the command says so before it asks, and hermetic doctor warns while the file exists.

High

No production deployments yet

Hermetic is pre-release software. The test suite gives confidence; it is not real-world mileage.

High

No independent human security audit yet

AI-driven red-teaming is not a substitute for an audit by a named firm. One is planned after launch.

Medium

Linux only, x86_64

The design depends on Linux kernel features — peer credentials on Unix sockets, memory locking, /proc. No macOS or Windows build.

Medium

Containers need the memory-lock capability

The daemon refuses to start if it cannot lock its memory, and most container runtimes drop that capability. In Docker, add --cap-add=IPC_LOCK.

Out of scope by design: root or a compromised kernel can read any process's memory, and a weak passphrase can be brute-forced if the vault file is stolen. Passphrases must be at least 12 characters.

FAQ

Questions people ask first.

Can I install Hermetic today?

Not yet. Hermetic is in a private pre-release; the public repository and downloads are paused while v1.3 is prepared. Join the waitlist and you'll hear when it ships.

Does the agent really never see my key?

On the default path, yes: the agent sends a key name and a URL, and Hermetic's own processes decrypt the key, make the call and return the response. No MCP tool returns a key value, and there is no tool to store or reveal one. The table under “How it works” lists exactly which Hermetic process holds the key on each path. If you allow a key to be handed to a program, that program holds it while it runs — which is why that is off by default.

Which agents does it work with?

Claude Code, Cursor, Windsurf and Claude Desktop are configured by hermetic connect; VS Code and any other MCP client that speaks stdio work through hermetic mcp-config. OpenClaw gets both the MCP tools and an exec credential provider. hermetic shield can run any command-line agent, for example claude or codex.

Is the free edition less secure?

No. Every security control — encryption, the shield, per-key rules, the destructive-endpoint floor, the audit log, process hardening — is in both editions. Community limits capacity (10 keys, one environment, a 7-day audit view); Pro adds credential types and tooling.

Does Hermetic send any data anywhere?

No. There is no telemetry, no analytics and no cloud account. The only network traffic is the API calls you or your agent ask it to make. Your vault never leaves your machine.

How is this different from a password manager or a secrets vault?

Those tools hand the secret to whoever asks — a person, a script or an agent — and trust them with it. Hermetic uses the secret on the caller's behalf and returns the result, with per-key rules and an audit trail in between. They work well together: keep your vault for humans, and let Hermetic broker what your agents use.

Can I read the source?

The cryptographic core and the transport layer are open source under AGPL-3.0-or-later; their public source returns with the public release. The daemon and the agent-facing layers are proprietary, distributed as free and paid binaries with the same security model.

What happens if I forget my passphrase?

The vault cannot be opened — there is no recovery key and no reset by us, by design. Keep the passphrase in your password manager. hermetic reset destroys the vault so you can start again.
